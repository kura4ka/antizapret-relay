# Архитектура VPS relay

Проверено по [AntiZapret-VPN](https://github.com/GubernievS/AntiZapret-VPN) на коммите
`aabea42bb51520371c8afc2b9b82cc6966068660`.
В upstream заявлена поддержка Debian 13 и Ubuntu 24.04 или новее.

Сервер 1 — входной VPS с установленным AntiZapret: к нему подключаются
VPN-клиенты, на нём модуль запускается в режиме `client`. Сервер 2 — выходной
VPS, через который выбранные сайты получают трафик: на нём используется
режим `server` (донор). Оба VPS могут находиться в любых странах и у любых хостеров.
Это роли в конкретном соединении: один VPS может одновременно быть клиентом
другого донора и донором для входящих соединений.

## Совмещение клиента и донора

На одном VPS клиент использует штатные `warp-antizapret` и `warp-vpn`,
а донор использует отдельный интерфейс `az-relay`. Состояние, ключи и
правила firewall каждой роли сохраняются отдельно. Установка, восстановление
и удаление клиентской роли не удаляют интерфейс или настройки донора.
При наличии обеих ролей удаление выбирается явно:
`antizapret-relay uninstall --role client` или
`antizapret-relay uninstall --role server`.

Донор автоматически выбирает свободную транзитную подсеть `/24`, используя
свой endpoint как начальное значение и проверяя существующие локальные
маршруты. Выбранная подсеть сохраняется вместе с ключами и при обновлении
работающего донора не меняется. Одинаковые подсети разных доноров всё же
могут совпасть: клиент проверяет импортируемую подсеть и при конфликте
отказывается от установки до изменения работающего AntiZapret.
Установщик не перенумеровывает действующего донора автоматически.

Донор сохраняет собственный экспорт ключей в
`/root/antizapret-relay-donor.json`. При ручной передаче клиент получает
bundle другого донора в `/root/antizapret-relay-import.json`; эти файлы
имеют разные имена и назначение. Интерактивный мастер может скачать
экспорт донора через `scp` с обычной проверкой SSH-хоста, применить его
из временного каталога с правами `0700` и удалить временный файл.
Это сохраняет собственный экспорт донора на VPS с двумя ролями.
Обе роли устанавливаются и обслуживаются независимо.

Запуск `bash install.sh` без аргументов открывает меню: `1` — клиент,
`2` — донор, `3` — обе роли. Уже установленные роли сохраняются.
В режиме обеих ролей донор настраивается первым; клиентскую роль можно
отложить до готовности другого донора. Успешно установленный донор
сохраняется и при ошибке последующего подключения клиента.

Трафик, полученный от другого клиента по `az-relay`, уже имеет транзитный
адрес источника. Поэтому он выходит через внешний интерфейс донора и
не попадает под штатные правила WARP для локальных VPN-клиентов.
Взаимное подключение само по себе не создаёт петлю между донорами.

Системные hooks вызывают `firewall up client` или `firewall up server`
для конкретной роли. Остановка `az-relay` вызывает `firewall down server`
и сохраняет защиту исходящего трафика клиентской роли. При добавлении
второй роли или обновлении установщик заменяет старые общие hooks на
вызовы соответствующей роли, сохраняя ключи и остальные настройки.

## Использование штатной маршрутизации

Модуль заменяет удалённый WireGuard endpoint штатных интерфейсов
`warp-antizapret` и `warp-vpn` на собственный VPS. Названия интерфейсов
и параметров WARP сохраняются ради совместимости с AntiZapret.

В `/root/antizapret/setup` задаются все четыре параметра каждого выбранного
интерфейса: `*_WARP_PRIVATE_KEY`, `*_WARP_PUBLIC_KEY`, `*_WARP_ENDPOINT` и
`*_WARP_ADDRESS`. Пока все четыре значения заполнены, `up.sh` не обращается
к Cloudflare для регистрации. Для выборочной маршрутизации используются
`ANTIZAPRET_WARP=4` и `VPN_WARP=3`.

Штатные `proxy.py` и Knot Resolver продолжают выдавать fake IPv4 из
настроенного диапазона AntiZapret, выполнять DNAT и ставить mark `0x2`.
Это сохраняет клиентские профили и не требует второго аллокатора fake IP.
`wg-quick` использует таблицы 1000 и 2000; штатные правила с priority 10000
отправляют туда только нужные клиентские пакеты. Основная таблица маршрутов
VPS остаётся доступна для SSH и внешних UDP-пакетов WireGuard.

Для `warp-antizapret` и `warp-vpn` создаются **разные клиентские ключи** и
разные транзитные IPv4 `/32`. Два интерфейса с одинаковым клиентским ключом
заставили бы один серверный peer постоянно менять UDP endpoint.
На выходном VPS достаточно одного отдельного WireGuard-интерфейса с двумя
peers, у каждого `AllowedIPs` содержит только его транзитный `/32`.

Сервер 1 выполняет штатный SNAT клиентских адресов в соответствующий транзитный
адрес. Сервер 2 выполняет MASQUERADE трафика этих peers через свой внешний
интерфейс. Поэтому одинаковые клиентские подсети AntiZapret на двух VPS
не конфликтуют, а правила WARP на сервере 2 по клиентскому source не захватывают
транзитный трафик.

## Выбор доменов

Основные пользовательские списки находятся **на клиентском VPS**:
`/root/antizapret/config/include-warp-hosts.txt` задаёт домены для выхода
через донора, а `/root/antizapret/config/exclude-warp-hosts.txt` — исключения.
После редактирования запускается `/root/antizapret/parse.sh`. Он пересоздаёт
DNS-политики, очищает серверные DNS-кеши и переподключает WARP-интерфейсы.
Запись домена включает сам домен и его поддомены. Исключённые домены
обрабатываются по остальным правилам AntiZapret.

Установка клиента с одним `--bundle` сохраняет существующие штатные списки;
параметр `--domain` необязателен. Дополнительные команды `domain add|remove|list`
управляют только файлом `config/relay-include-warp-hosts.txt`. Его обрабатывает
тот же штатный `parse.sh` вместе с другими файлами, подходящими под
`config/*include-warp-hosts.txt`; `domain list` не выводит общий результат.

Механизм намеренно использует **общие штатные списки WARP**. В результат
также входят существующие пользовательские записи и
`download/*include-warp-hosts.txt`; в проверенном upstream там присутствуют
`cloudflare.com` и несколько STUN/TURN-доменов. Штатные исключения из
`config/*exclude-warp-hosts.txt` продолжают действовать. Таким образом,
модуль меняет выход для всей группы, выбранной штатным механизмом WARP,
а не создаёт параллельную независимую группу доменов.

Настройка `DNS_WARP` и DNS-параметры остаются без изменений. Следовательно,
география DNS-ответов по умолчанию определяется существующей настройкой сервера 1.
Если отдельно настроить `DNS_WARP=y` со своим третьим peer, через сервер 2 пойдут
**все** исходящие DNS-запросы Knot, а не только запросы выбранных доменов.

## Сбои и обновления

`wg-quick up` проверяет создание интерфейса, но не успешный handshake и
не доступность сайта. Штатная надпись `connected` не является проверкой
связности. `WARP_PROTECTION=y` блокирует клиентскую подсеть при ошибке
создания интерфейса; этот механизм сам по себе не контролирует дальнейшее
состояние туннеля.

Штатный `parse.sh` пересоздаёт WARP-интерфейсы через
`wg-quick down ... && wg-quick up ...`. В промежутке и после удаления
интерфейса таблица маршрутов может потерять default route и разрешить
переход к основной таблице. Поэтому защита модуля должна отдельно
запрещать выбранный трафик, когда он пытается выйти через другой
интерфейс. Автоматическое переключение на другой VPS не реализовано.

Ежедневный `doall.sh` сохраняет `/root/antizapret/setup` и пользовательские
списки. Повторная установка полным `setup.sh` пересоздаёт каталог
`/root/antizapret` и очищает параметры удалённых WARP peers. После такой
переустановки конфигурацию relay требуется применить заново; резервная
копия и состояние модуля должны находиться за пределами этого каталога.

При применении и восстановлении настроек AntiZapret нужно сначала
остановить с исходным `setup`, затем менять параметры и запускать снова.
Иначе `down.sh` может удалять правила NAT по новым адресам, оставив правила
для прежнего peer. Восстановление должно менять только параметры,
которыми управлял модуль, сохраняя последующие несвязанные изменения.
